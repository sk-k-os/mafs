# Six account Codex transport evidence

Revision 2. Research date: October 28, 2026. Design only.

Recommend six separately authenticated Codex execution lanes, each with a dedicated local app server and private Codex state directory. A Mathforge broker should assign bounded work, exchange reviewed artifacts, preserve account attribution and enforce one campaign budget across all six lanes. Account identity, agent identity, research role and mathematical authority remain separate.

The official documentation supports the underlying authentication, configuration and transport features. It does not establish that this six account composition has been tested, that six subscriptions provide six times a predictable capacity, or that identities and quotas are independent in the director's actual setup. Those are acceptance tests for a later implementation.

## Evidence and inspection boundary

Used the OpenAI Docs skill. Read current official pages on authentication, configuration, app server and pricing. Initially inspected these local CLI interfaces:

1. `codex --version`
2. `codex app-server --help`
3. `codex login --help`
4. `codex app-server generate-json-schema --help`
5. `codex exec --help`

The installed binary reports `codex-cli 0.155.0-alpha.9.2`. Its help exposes app server stdio transport, schema generation, login status and device authentication. A subsequent design inspection reviewed protocol types generated by the parent task with `codex app-server generate-ts --out work/codex-protocol`, without `--experimental`. This is static public interface generation, not a server or account operation. No server, inference turn, login flow, authentication status request or quota request was started. No credential file, existing configuration, environment secret or keychain entry was read. No account has been validated by this report.

## Documented facts

**State locations.** `CODEX_HOME` selects Codex's local state root. This includes configuration, history and other state. Project `.codex/config.toml` files can add overrides. A configuration profile layers settings; it is not documented as a separate authentication identity. [Advanced configuration](https://learn.chatgpt.com/docs/config-file/config-advanced)

**Authentication storage.** Native ChatGPT authentication manages refresh. The `file` credential mode stores `auth.json` under `CODEX_HOME`; `keyring` requires the OS credential store; `auto` can fall back to a file; `ephemeral` retains credentials only in the current process. The documentation describes cached credentials as sensitive and notes that the CLI and extension can share their cache. It does not specify a six directory keyring isolation contract. The browser flow normally uses a localhost callback; device authentication is another documented option. [Authentication](https://learn.chatgpt.com/docs/auth)

**Configuration controls.** `forced_login_method = "chatgpt"` restricts authentication type. `forced_chatgpt_workspace_id` restricts a workspace when the correct identifier is known; it is not a general individual account selector. `cli_auth_credentials_store` can also be enforced through local system requirements or MDM. Do not assume a user config can override managed requirements. [Configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference)

**Protocol.** The app server provides JSON messages over stdio, an initialization handshake, thread and turn operations, account inspection and quota inspection. `account/read` documents account type, nullable email and plan type; its example does not guarantee a stable account identifier. `account/rateLimits/read` and `account/rateLimits/updated` expose quotas. Prefer `rateLimitsByLimitId` when present; `usedPercent` is consumed capacity and `resetsAt` is epoch seconds. `model/list` exposes model choices. External token authentication is experimental. TCP WebSocket transport is explicitly described as experimental and unsupported, with additional exposure hazards. [App server documentation](https://learn.chatgpt.com/docs/app-server)

**Billing.** ChatGPT Work and Codex share usage. API key sessions use separate API billing. Additional ChatGPT credits and API key use are documented ways to extend work after included limits; they are not a promise of automatic free fallback. An active turn may continue after a limit is reached, subject to fair use. [Pricing and usage](https://learn.chatgpt.com/docs/pricing)

**Integration fit.** OpenAI distinguishes bounded `codex exec` work from product integrations needing app server lifecycle control and streamed events. The surrounding application owns its domain records, tools and controls. That supports using a separate Mathforge broker rather than making terminal text the system of record. [Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform)

## Exact evidence from the installed protocol

The following findings come from the generated types for `codex-cli 0.155.0-alpha.9.2`, not from live account responses. Source root: `<private inspection workspace>/codex-protocol`. Generated types establish the local interface shape and documented comments; they do not establish which optional values the backend will supply for the director's accounts.

| Generated source | Observed fields and limits |
| :--- | :--- |
| `v2/GetAccountRateLimitsResponse.ts` | `ordinaryUsageAllowed: boolean \| null`; `accountId: string \| null`; `rateLimits`; nullable `rateLimitsByLimitId`; nullable `rateLimitResetCredits`; nullable `rateLimitUpsell`. The permission comment says the backend validates ordinary included usage against the active account and prohibits inferring recovery from percentages or reset times. The ID comment ties it to this usage snapshot when the backend supplies it. |
| `v2/RateLimitSnapshot.ts` | Nullable `limitId`, `limitName`, `normalModelSlug`, `primary`, `secondary`, `credits`, `individualLimit`, `spendControlReached`, `planType` and `rateLimitReachedType`. The spend control comment says an unavailable value is not recovery through a sparse update. `normalModelSlug` identifies the normal model used to describe a quota alias; it is not an extra account identity or an entitlement grant. |
| `v2/SpendControlLimitSnapshot.ts` | `limit` and `used` are strings; `remainingPercent` and `resetsAt` are numbers. These types alone do not establish a currency, price conversion or billing precision policy. Preserve raw values and their source context until those semantics are qualified. |
| `v2/Account.ts` | The ChatGPT variant has nullable `email` and `planType`; no account ID field is present. Other variants identify API key or Bedrock authentication. Do not claim that `account/read` provides an ID merely because the separate usage response can. |
| `InitializeResponse.ts` | `codexHome` is the server's absolute state root, alongside `userAgent`, `platformFamily` and `platformOs`. This allows a startup check against the expected private root before work is admitted. It does not identify the signed in account. |
| `PlanType.ts` | The enum includes `pro` and `prolite`, among other plan labels. A generic `pro` value does not establish the paid price tier or exact capacity of a Pro subscription. |

Use `ordinaryUsageAllowed === true` as necessary backend evidence for ordinary included usage in the proposed scheduler. It is not sufficient for dispatch: account binding, freshness, spend controls, task authorization and local budgets must also pass. `false` holds ordinary dispatch. `null` means permission is unavailable; do not substitute low utilization, an elapsed reset time, credits or optimistic heuristics. For this design, hold new ordinary dispatch until a fresh, reconciled permission is available. A stale response must not override a newer account change or denial.

For a relevant bucket, `spendControlReached === true` blocks work covered by that control. `false` does not establish ordinary usage permission. `null` supplies no affirmative recovery signal and must not clear an existing hold. If spend control status is mandatory for the selected spending mode but unavailable, retain the hold and explain the missing evidence. Apply the same explicit unknown handling to missing windows, credit data, reset credit data and plan labels. Reset credit availability is not authorization to consume one.

The nullable usage `accountId` can strengthen identity pinning. During enrollment, associate a supplied ID with the operator confirmed identity only after reconciling the usage snapshot with the same lane's active auth state and process generation. Serialize auth mutations while that reconciliation is underway. On a changed ID, conflicting auth event, null identity that cannot be reconciled, or stale snapshot, hold the lane and revalidate; never silently reassign the alias. This process supplements the nullable email and plan metadata rather than decoding credentials.

Quota pool keys, `limitId` values such as `codex`, and model quota aliases are not account IDs. They can repeat across accounts. Key stored quota evidence by lane, reconciled account identity when available, process generation, bucket and observation revision. Do not infer shared or independent entitlements solely from matching or different pool names.

## Proposed isolation contract

Use stable local aliases `account01` through `account06`. They are opaque Mathforge labels, not claims about OpenAI account IDs. An account registry should hold the alias, operator confirmed identity reference, reconciled usage account ID when supplied, selected workspace when available, state root, process binding, configuration digest, auth mode, last verification time and availability. Preserve the provenance and null state of every optional identity field. Do not put credentials in that registry.

Suggested private state root for each lane:

`<private-state-root>/mathforge/accounts/01/codex`

The other five lanes receive corresponding distinct paths. These paths are a design proposal and were not created. They sit outside the research repository, shared artifact tree and HUD assets. The eventual launcher should set `CODEX_HOME` only in the child process environment. It must not change the director's global shell configuration or repoint the desktop app.

For the first controlled implementation, explicitly select native managed ChatGPT authentication and the `file` credential store for each dedicated lane. This provides a documented per directory storage location rather than relying on undocumented keyring naming. The tradeoff is a sensitive plaintext credential cache. Require private directory permissions, encrypted host storage and exclusion from repository commits, ordinary artifact backups and support bundles. The application must never parse or copy the cache into broker messages.

Different directories and file permissions under one OS user are organizational separation, not a complete security boundary against code executing as that user. Before enabling arbitrary mathematical scripts or generated proof tooling, enforce and test a host sandbox that prevents tool processes from reading all six credential roots, broker secrets and peer workspaces. Alternatively use separate OS principals or isolated worker hosts with tightly scoped broker channels. A prompt telling an agent not to read credentials is insufficient.

Use one process owner per account home. Keep authentication mutations serialized, and avoid sharing a home with unrelated CLI, IDE or desktop sessions. Do not let candidate code change account settings or invoke login/logout. The app server process needs access to its own authentication storage; generated tool processes do not need access to credential contents.

Before implementation, check whether managed policy allows the selected storage mode. If it forces keyring, qualify keyring separation on the actual OS and pinned CLI instead of silently switching modes. No evidence found here establishes that keyring necessarily collides; the issue is an unverified isolation guarantee.

Authenticate the six accounts sequentially during an explicitly requested onboarding step. This reduces browser session confusion and callback conflicts. Display each intended alias and verify the returned nonsecret identity metadata with the director. A missing or ambiguous identity field requires operator reconciliation, not token decoding or invented IDs. Changes to account or workspace invalidate that lane's previous admission.

## Broker and terminal design

Six terminal windows are useful operator views. They should each show a named lane, assigned role, current task, quota freshness and connection state. The transport underneath should be six dedicated child app server processes using stdio. Do not send keystrokes between terminal windows or scrape prose to reconstruct task completion.

The broker owns dispatch, leases, task dependencies, artifact references, cancellations, budgets and append only operational events. Each lane can host successive specialist roles. Start with one active bounded assignment per lane; additional concurrency requires measured resource and quota behavior. No seventh paid coordinator model is inherently required: deterministic coordination remains a broker service, and model based planning can consume one of the six lanes when needed.

Keep each account's conversation state private. Within one lane, retain its local thread identity for resumption. Across lanes, transfer a reviewed handoff packet and start a receiving conversation; do not assume a thread identifier from one home is portable to another. Never transfer authentication files or copy the entire private home as research memory.

A proposed broker envelope contains:

1. `messageId`, `campaignId`, `assignmentId`, revision and schema version.
2. Sender and receiver lane aliases plus worker instance IDs and role definitions.
3. Message kind, exact objective, input artifact hashes, assumptions, objections and output requirements.
4. Lease ID, attempt number, deadline, cancellation revision and remaining campaign allocation.
5. Optional local thread and turn locators namespaced by lane and process generation.
6. Receipt and acknowledgement state without credentials or raw authentication payloads.

This envelope is Mathforge's proposed contract, not an OpenAI protocol object. An adapter maps it to the pinned app server schema. Broker methods must never be presented as if they were existing Codex methods.

Use immutable artifact references and acknowledgements. An interrupted request has an unknown effect until reconciled. Do not blindly resend a turn and accidentally duplicate tool side effects. Preserve dispatch, acknowledgement, completion and cancellation as separate states. Reject stale completion receipts from previous leases or process generations.

Account status is operational evidence. Accepted mathematics still belongs to the trusted evidence service and its required verification receipts. The broker cannot promote a theorem because an account completed a turn. Multiple accounts running the same model remain correlated; blind review, distinct approaches, exact computations, proof checking and the director's direction remain necessary.

## Minimal proposed adapter surface

Use these documented protocol names when binding the actual pinned schema: `initialize`, `initialized`, `account/read`, `account/updated`, `account/rateLimits/read`, `account/rateLimits/updated`, `model/list`, `thread/start`, `thread/resume`, `turn/start`, `turn/interrupt` and `turn/completed`. An `auth/read` method was not identified in the inspected official documentation. Treat that name as unsupported unless the pinned generated schema establishes it. [App server API](https://learn.chatgpt.com/docs/app-server)

The inspected generated types are design evidence. During implementation, bind and version the exact approved schema with the adapter; regenerate and review differences before upgrades. A type present in current online documentation is not proof that every deployed binary implements it. Compare the returned `codexHome` against the intended lane root at initialization, including an explicit path normalization policy; reject a mismatch before any assignment.

Keep authentication administration outside ordinary worker tool access. The initial adapter should use native managed login rather than experimental externally supplied tokens. This avoids making Mathforge responsible for reading, distributing and refreshing user tokens. Future OAuth integration would be a separate reviewed capability.

Quota events should update each lane separately and follow their own pinned payload schema; do not assume every notification contains the complete read response. Missing or stale fields mean unknown capacity and cannot clear a previous denial. Neither an average percentage nor the sum of six percentages is a meaningful combined token allowance. HUD summaries should show backend ordinary usage permission, spend control state, identity reconciliation, available windows, reset time, account mode, freshness and credit state, with local campaign limits alongside provider limits. Show `unknown` for null fields.

## Billing and stopping behavior

The proposed default is subscription authentication only, with API fallback disabled. Enforce this with both configuration and observed auth mode. Launch using an approved environment allowlist; do not inherit API credentials or arbitrary provider overrides from the broker shell. The exact environment rules must be tested against the pinned executable.

Available ChatGPT credits can affect spending even while authentication remains ChatGPT based. A claim of “subscription only, no additional spend” requires a verified funding boundary. Until then, show incremental monetary cost as unknown and keep autonomous included only dispatch unavailable. Use simulated transport to test unknown and credit funded states. A short assignment alone cannot prevent spillover. Do not equate token telemetry with a billing receipt.

When a lane cannot accept work, hold its queue, preserve the task checkpoint and show the reason. A separately authorized available lane can receive a new assignment with the same campaign accounting and preserved context. Do not assume a new account alias resets OpenAI limits or the local campaign budget. If all lanes are unavailable, pause dispatch. Do not purchase credits, redeem resets, change authentication method or trigger account notification emails automatically.

Any later API fallback should be explicit: separate credential binding, account/project attribution, spending cap, allowed models and human authorization. Switching modes can change both billing and data controls. Reusing the same visible lane name must not hide that change.

## Six account admission tests required later

| Test | Required observation |
| :--- | :--- |
| Identity separation | Each alias matches the intended signed in person and workspace using supported metadata and operator confirmation. When present, the usage account ID is reconciled and pinned. Duplicate, stale, conflicting or unresolved null identity evidence blocks admission. |
| State root binding | Initialization reports the expected `codexHome` after the agreed path normalization. A wrong root blocks dispatch. |
| Authentication isolation | Logging out, restarting or refreshing one lane does not change another lane's identity or session. |
| Credential protection | Generated tool processes cannot read any credential root or broker secret; logs and HUD contain no credentials. |
| Configuration isolation | Project overrides, inherited environment and managed policy cannot silently change a lane's provider or auth type. |
| Independent state | Threads, resumptions and account state remain in the intended lane across a restart. Cross lane recovery uses explicit handoff. |
| Model access | A bounded authorized smoke turn succeeds on the selected model for each account. A catalog listing alone is not treated as a completed inference entitlement check. |
| Quota semantics | Ordinary usage permission, spend control state, window fields, resets and nullable data are handled separately. Elapsed resets or low percentages never imply recovery; pool names never substitute for account identity. |
| Spending behavior | Simulated limit, credit and missing credential states exercise the control. Later live qualification must stay within verified authorization and must not consume real credits to test a failure. Unknown funding boundaries hold autonomous dispatch. |
| Transport recovery | Process death and connection loss do not create duplicate accepted results or untracked repeated side effects. |
| Budget integrity | Six parallel lanes and all replacements consume one cumulative campaign allocation with account level attribution. |
| Review separation | A reviewer cannot access another review before committing its own; account multiplicity is never scored as proof independence. |
| Operator interaction | the director can pause a lane or campaign, inspect a disagreement and supply direction without erasing receipts or restarting budget accounting. |

The six accounts' owners, plan types, entitlements, credit settings, actual remaining capacity and workspace relationships remain uninspected. Nothing in this document establishes that an autonomous multiaccount service is running.
